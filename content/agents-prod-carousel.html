The real difference
DEMO WORKS ONCE.
PROD WORKS ALWAYS.
A demo agent impresses in a controlled setting. A production agent survives real users, bad inputs, API outages and unexpected tool failures, without breaking.
Demo agent
  • Happy path only
  • No error handling
  • No logging or tracing
  • No memory across sessions
  • No guardrails
  • Crashes on bad input
Production agent
  • Handles edge cases
  • Retries + fallbacks
  • Full trace on every run
  • Persistent memory
  • Guardrails on every action
  • Gracefully degrades

The checklist
6 THINGS THAT
MUST BE TRUE.
Before you call an agent "production-ready", it needs to pass all six. Not five. Six.
1
It handles tool failures gracefullyAPIs go down. Networks time out. Your agent must retry, fall back, or report, never crash silently.
2
Every run is observableYou can see exactly what the agent did, which tools fired, and what the model returned, on any past session.
3
Memory persists across sessionsThe agent remembers what it did last time. Users do not re-explain context on every new conversation.
4
Guardrails block dangerous actionsHigh-risk tools, delete, send, charge, need human approval before they fire. Not optional.
5
It stays within token limitsLong sessions eat context. The agent compresses history intelligently instead of cramming the window.
6
You can evaluate it systematicallyYou have a test suite. You know if a change made the agent better or worse before it ships.

Step 1 · The foundation
PICK THE RIGHT MODEL.
WRITE THE RIGHT PROMPT.
The model and the system prompt are the brain of your agent. Get these wrong and no amount of tooling will save you.
1
Do not default to the biggest modelMatch model to task. Claude Haiku is fast and cheap for simple routing. Sonnet for nuanced reasoning. Opus for the hardest tasks. Stay model-agnostic.
2
The system prompt is load-bearingDefine the agent's role, constraints, tone and tool rules in a clear system prompt. Vague prompts produce vague agents. Specific prompts produce predictable agents.
3
Use a context file the agent reads every sessionProject context, conventions, team preferences, business rules, loaded on every run. The agent stops asking what it already knows.
Rule of thumbStart with a small model + a great prompt. Upgrade the model only when the prompt ceiling is genuinely hit. Most failures are prompt failures, not model failures.

Step 2 · Tools
TOOLS FAIL.
PLAN FOR IT.
Every tool call in production will eventually fail. Wrap every single one with retry logic, a timeout and a fallback before your agent ships.
Wrap every tool call · retry pattern
from tenacity import retry, stop_after_attempt, wait_exponential

# every call gets retries, a timeout and a fallback
@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, max=10))
def search_web(query: str) -> str:
    try: return tavily.search(query)
    except Exception as e:
        return "Search unavailable. Try a different approach."
# the agent sees the error as text and works around it, never crashes
+
Keep tools focusedOne tool, one job. Fewer than 8 tools per agent. Vague tools mean the wrong tool gets chosen. Clear descriptions, reliable routing.
!
Never retry on 4xx errorsRetry on 5xx and network failures only. Retrying a 400 Bad Request just burns tokens faster.

Step 3 · Memory
AGENTS WITHOUT
MEMORY START OVER.
An agent that forgets every session is not useful in production. Memory is what turns a one-shot tool into a system users trust.
Short-termWorking MemoryThe active conversation window. Compress it before it overflows, checkpoint the thread, never lose the live context.
SemanticVector MemoryDocuments and knowledge searched by meaning, the foundation of RAG. Pinecone, pgvector, Weaviate.
Long-termPersistent MemorySurvives across sessions. Preferences, project rules, past decisions. Mem0, LangGraph Store, Zep.
SkillLearned ConventionsUser corrections, patterns and team rules stored in a context file, loaded every session.

Step 4 · Observability
IF YOU CAN'T SEE IT
YOU CAN'T FIX IT.
Every agent decision in production must be traceable. Without logs and traces, debugging a silent failure means guessing.
Enable tracing · 2 lines
import os
os.environ["TRACING_V2"] = "true"
os.environ["TRACING_API_KEY"] = "your key"
# every agent run is now auto-traced: every tool call, every token, every decision

import logfire
logfire.configure()
# one logfire line for structured logs on top
+
What to trackLatency per step, tokens used, tool success rate, answer quality. The four numbers that explain every failure.
+
Tools that do itLangSmith, Logfire, Arize. All integrate in 2 lines. Full trace trees, structured search over every run.

Step 5 · Safety
THE AGENT DECIDES WHAT.
YOU DECIDE WHAT'S SAFE.
The model picks the action. Your guardrails decide if it is allowed. These are architecturally separate, and they must be.
1
Input guardrailsValidate user requests before the agent acts. Block harmful, out-of-scope or malformed inputs at the front door.
2
Human-in-the-loop · pause before the actionHigh-risk tools (send email, delete file, charge card) pause the agent and wait for human approval. The agent resumes with full context, exactly where it stopped.
3
Output guardrailsFinal check before the result reaches the user. Catch hallucinations, policy violations or incomplete answers, before they ship.
Start hereDefault to supervised: the agent acts, a human approves the high-risk steps. Earn full autonomy by proving reliability over time.

Step 6 · Evals
TEST YOUR AGENT
LIKE SOFTWARE.
You would not ship code without tests. Do not ship agents without evals. Evals tell you if a change made the agent better or worse, before your users find out.
1
Build a golden dataset50-100 real inputs with expected outputs. Every change to the agent runs against this. Green means ship. Red means fix.
2
Test failure modes specificallyBad inputs, API timeouts, ambiguous queries, very long sessions. If it can happen in production, test it before production.
3
Use LLM-as-judge for qualityFor open-ended answers, a second model scores accuracy, completeness and relevance. Scales to thousands of evals per run.
ToolsLangSmith Evaluations · Braintrust · OpenEvals · Ragas (for RAG) · pytest with LLM assertions
